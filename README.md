# MingLi-Bench · 紫微斗数人格画像的确定性引擎与评测

[命理鉴心](https://minglijinxin.com)（作者独立开发、已上线运营的 AI 人格分析与付费问答平台）的报告原本由 LLM 一次性做两件事：**算**（六维人格分、24 个三国人物里匹配哪一个）和**说**（解读正文）。本仓库把「算」从 LLM 里拿出来做成确定性代码，并用可复算的评测说明为什么要这样做：

```
出生信息 ──► iztro 排盘 ──► 确定性引擎（本仓库）──► 事实 JSON（分数 + 人物 + 每条依据）──► LLM 只写解读
```

```bash
npm ci
npm test               # 42 个测试
npm run simulate       # 21,600 张命盘上评测规则表 v1 / v2（约 10 分钟）→ results/SIMULATION.md
npm run crosscheck     # 排盘交叉验证：iztro vs 独立实现 → results/CROSSCHECK.md
npm run llm:analyze    # 重算 DeepSeek 评测（只读已落盘的原始输出，不调 API）
npm run llm:compare    # 跨模型 / 线上复现对比 → results/LLM_COMPARE.md
npm run llm:recall     # 校验器召回率估计 → results/llm/RECALL.md
npm run build          # 打包成 dist/mingli-engine.cjs（Node 18+ 可直接 require，产品后端用）
```

开发需要 Node.js ≥ 22.18（直接运行 TypeScript）；打包产物支持 Node 18+。

## 结论速览

| 问题 | 证据 | 结论 |
|---|---|---|
| 线上 LLM 自己算，结果稳定吗？ | 线上免费档忠实复现，10 张盘 × 3 次 | **六维分 0/10 张盘一致**，人物 6/10 一致 |
| LLM 会按规则表选人物吗？ | 盘上存在完全匹配人物时 | 线上复现 3/12；DeepSeek / Haiku / Sonnet 各 1/4；**引擎 4/4** |
| 换更强的模型能解决吗？ | 跨模型对比 | 不能。Sonnet 选得更「沾边」，但同样只有 1/4 选中完全匹配 |
| 引擎接管计算后，解读质量会变差吗？ | 同模型 30 份对比 | 不会。盘面陈述判错率 0.2%（LLM 自算组 0.4%），字数和耗时持平 |
| 规则表本身没问题吗？ | 21,600 张盘分布模拟 | 有问题：「刘备」**可证明**永远无法完全满足；只有 32.89% 的盘能完全匹配某个人物；六维分整体偏低 |
| 排盘库可靠吗？ | 与独立实现交叉验证 | 2,100 张盘、73,500 项比对，**0 不一致** |

## 1. 引擎

```ts
import { profileFromBirth } from './src/index.ts';

const r = profileFromBirth({ date: '2000-8-16', hourIndex: 2, gender: '女' }, { rules: 'v1', refDate: '2026-6-1' });
r.scores;     // { 自我觉察: 3, 情绪调节: 4, 延迟满足: 3, 关系模式: 3, 不确定性容忍: 1, 自我叙事: 3 }
r.persona;    // { name: '徐庶·孝义', fullMatch: false, matched: [...], unmatched: ['命宫三方四正见文昌'], ... }
r.facts;      // 交给 LLM 的事实 JSON（含每个维度、每个宫位的加减分依据）
r.chartText;  // 交给 LLM 的命盘文本（含亮度、杂曜、长生、大限，亮度写作「太阴[不]」避免歧义）
```

| 路径 | 内容 |
|---|---|
| `src/scores.ts` | 六维分。v1 = 原提示词 `SCORES_RUBRIC` 的忠实实现；v2 = 修订提案 |
| `src/persona.ts` | 24 人物。v1 = 原提示词 `PERSONA_MAPPING` 逐条改写；v2 = 核心/辅助条件分层 + 刘备修订 |
| `src/normalize.ts` | iztro → 引擎内部结构（与排盘库解耦）；附带参考时点的大限、流年四化与十干四化表 |
| `src/product.ts` | 产品入口：出生信息校验、命盘文本、事实 JSON、最终 SCORES/CARD 标记 |
| `src/citation.ts` | 引用校验：从 LLM 正文抽取盘面陈述（星在宫、四化、亮度）并与命盘核对 |
| `docs/RULES.md` | v1：原文歧义的逐条解读，以及规则表缺陷 |
| `docs/RULES-v2.md` | v2：修订内容、选型依据与分布对比 |

## 2. 规则表评测（21,600 张盘）

样本：iztro 排出的 1960–2009 年、每月 1/11/21 日 × 12 时辰的全部命盘。详见 [`results/SIMULATION.md`](results/SIMULATION.md)。

**v1（原规则）的问题**：

1. **「刘备」永远无法完全满足**：要求紫微与天同或太阴同在命宫三方四正，但紫微与它们的位置差恒为奇数，三方四正内只能是偶数。证明见 `docs/RULES.md`，已写成测试。
2. **按「同宫」解读，5 条规则不可能成立**（赵云、刘备、贾诩、孙策、鲁肃）。
3. **只有 32.89% 的盘能完全匹配某个人物。** 原提示词要求「严格对照、不可自行发挥」，三分之二的用户做不到。
4. **六维分整体偏低**：5 分在各维度只占 0%–2.6%。

**v2（修订提案，待产品负责人审核）**：规则分「核心条件」与「辅助条件」两层，刘备改为可满足，六维分锚点重新校准。

| 指标 | v1 | v2 |
|---|---|---|
| 选中人物的核心条件全部满足 | — | 85.01% |
| 选中人物完全匹配 | 32.89% | 33.87% |
| 刘备可完全满足 | 不可能 | 1.09% 的盘 |
| 六维分均值（各维度） | 2.40–2.59 | 3.21–3.28 |
| 人物被选比例（最多 / 最少） | 10.69% / 0.69% | 10.98% / 0.70% |

人物分布不均的问题 v2 没有解决，原因在 24 条规则本身宽严不一，需要产品决定。详见 [`docs/RULES-v2.md`](docs/RULES-v2.md)。

## 3. 排盘交叉验证

文墨天机对照数据尚未提供。在那之前，用另一条独立路径核对 iztro：农历换算用 lunar-javascript，安星按安星诀独立实现（命身宫、五行局、十四主星、六吉六煞、禄存、生年四化），再与 iztro 逐项比对。

- 2,100 张盘（另有 60 张闰月盘跳过，iztro 的闰月处理规则不同），共 73,500 项，**0 不一致**。
- 比对逻辑做过变异测试：故意把文昌的安星公式改错一位，2,100 张盘里报出 195 次，说明「0 不一致」可信。

两套实现所依据的安星诀相同，所以这项验证能排除**实现错误**，不能排除**流派差异**（如火铃、魁钺的不同安法）。流派问题要靠文墨天机对照。详见 [`results/CROSSCHECK.md`](results/CROSSCHECK.md)。

## 4. LLM 评测

全部原始输出都在 `results/llm/raw/`，分析脚本只读这些文件，可以离线复算。

### 4.1 线上复现：用户实际拿到的是什么

照搬线上免费档：系统提示词从产品存档原样导出（`scripts/llm/prompt-free-prod.ts`），命盘文本照搬线上前端格式。线上前端的文本**没有亮度、杂曜、长生、大限，也没有出生日期**，而规则需要「庙旺」「天刑」「长生帝旺」等信息。DeepSeek（`deepseek-chat`，服务端实际返回 `deepseek-flash`），10 张盘 × 3 次。

| 指标 | 结果 |
|---|---|
| 同一张盘 3 次，六维分一致 | **0/10** |
| 同一张盘 3 次，人物一致 | 6/10 |
| 存在完全匹配人物时选中它 | 3/12（引擎 4/4） |
| 单维分与规则（引擎）完全一致 | 22%，平均相差 1.0 分 |
| SCORES/CARD 严格合规 | 29/30 |

免费档提示词还要求六维分「最高最低相差至少 2 分」，和打分锚点「不确定时一律 3 分」互相冲突。见 [`results/LLM_EVAL-deepseek-chat-prodtext.md`](results/LLM_EVAL-deepseek-chat-prodtext.md)。

### 4.2 LLM 自己算 vs. 引擎算好再解释（DeepSeek，各 30 份）

这一组用信息更全的命盘文本和存档中的 `lite.js` 精简提示词。注意：线上生成实际用的是 `profile-b.js`（精简档）与 `free.js`（免费档），三者共用同一套打分锚点、人物映射与标记规则。

| 指标 | LLM 自己算 | 引擎 + LLM 解释 |
|---|---|---|
| 同一张盘 3 次，人物 / 六维分一致 | 4/10 / **0/10** | 10/10 / 10/10（代码计算） |
| 存在完全匹配人物时选中它 | 2/12 | 4/4 |
| 所选人物一条条件都不满足 | 6/30 | 0 |
| 编出表外人物 | 1/30（「吕蒙」） | 0 |
| 盘面陈述判错 | 4/915（0.4%） | 2/949（0.2%） |
| 正文提到给定人物 | — | 29/30 |
| 平均字数 / 耗时 | 1,759 字 / 8.2 秒 | 1,731 字 / 8.6 秒 |

见 [`results/LLM_EVAL-deepseek-chat.md`](results/LLM_EVAL-deepseek-chat.md)。

### 4.3 跨模型（各模型 baseline 第 1 次）

| 指标 | 线上复现 | DeepSeek | Claude Haiku | Claude Sonnet |
|---|---|---|---|---|
| 存在完全匹配人物时选中它 | 1/4 | 1/4 | 1/4 | 1/4 |
| 所选人物平均条件满足率 | 56% | 34% | 42% | 61% |
| 所选人物零条件满足 | 1/10 | 4/10 | 2/10 | 0/10 |
| 单维分与规则完全一致 | 20% | 33% | 48% | 48% |
| 盘面陈述判错 | 0/123 | 0/314 | 4/304 | 0/334 |

Claude 两个模型是用 Claude Code 子代理（Claude 订阅额度）生成的，带有子代理自身的系统提示，和 API 调用的条件不完全相同；20 个子代理里有 3 个（都是 Haiku）多调用了与任务无关的工具，均被权限系统拦下，没有影响输出。见 [`results/LLM_COMPARE.md`](results/LLM_COMPARE.md)。

### 4.4 校验器本身准不准

- **精度**：所有被判错的陈述都人工复核过，都是真错误。四化陈述按生年、当年所走大限、当年流年，以及文中写明的年份或天干分别核对，避免把模型推得对的流年、大限四化误判为错。
- **召回率**：在真实报告里随机把主星名换成另一颗主星（共 800 处），校验器抓到 **52.6%**（下界）。替换处落在可核对陈述里的，抓到 79.4%。所以上面的「判错率」低估了真实错误率，大约要乘以 2，但仍然很低。见 [`results/llm/RECALL.md`](results/llm/RECALL.md)。

## 5. 产品接入（2026-11-25 已上线）

- 后端：`create-order` 接收出生信息，用引擎计算并保存结果；两条生成路径的提示词改为只写解读，最终的 SCORES/CARD 标记以引擎结果为准；`MINGLI_ENGINE=off` 可一键回退。同时修正了营收统计：按实付金额统计，排除测试单与免费单。
- 前端：下单时多传一个 `birth` 字段（真太阳时校正后的公历日期、时辰序号、性别）。
- 上线后验证：同一张盘独立生成 3 次（其中 1 次走真实浏览器的完整流程：填表、11 题问卷、下单、出报告），六维分与人物 3 次完全相同，报告末尾的标记与引擎结果一致。人物卡的副签名由模型撰写，每次不同，不在引擎管辖范围内。
- 接入代码见产品仓库的 `claude/engine-integration` 分支。

## 局限

- 排盘没有对照文墨天机，只做了独立实现交叉验证（见第 3 节）。
- LLM 评测样本小：每组 10 张盘，最多各 3 次。
- 规则 v1 的若干解读、v2 的全部修订都是设计决定，需要产品负责人审核（`docs/RULES.md`、`docs/RULES-v2.md`）。
